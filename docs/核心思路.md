## 一、原始提示词（产品由来，一字未改）

> 这是这个项目最初的那段构思，是「四个方向」的源头。保存它的原文，是为了不丢掉产品为什么长成这样。

```
# 项目：言外

## 一句话定位
一个运行在知乎网页上的划词解析工具，帮用户看懂看不懂的内容。

## 核心功能
1. 用户在知乎页面选中任意文本（问题、回答、评论）后，弹出悬浮气泡。
2. 气泡内调用 AI，从四个角度解析选中文本：
   - 术语解释：解释其中的专业名词或黑话。
   - 热点关联：说明相关的热点事件或历史背景。
   - 潜台词解读：结合上下文，解释这段话的隐含意思、梗或阴阳怪气。
   - 社区理解：当 AI 自身信息不足时，尝试结合知乎上其他用户的讨论和解读，给出更贴近真实用户视角的解释。
3. 气泡底部提供一个输入框，用户可以补充自己的理解或要求换个角度解释，AI 重新生成解析。
4. 界面简洁，参考知乎蓝白配色，气泡不遮挡正文。

## 技术栈
- 前端：油猴脚本（Tampermonkey），纯 JavaScript + CSS。
- 后端：Node.js 服务，负责处理请求、调度模块、调用 AI。
- 前端通过 GM_xmlhttpRequest 调用后端接口。
- 不需要数据库，但保留数据存储模块的接口。

## 架构设计
- 前端 / 后端两部分：前端负责划词监听、气泡展示、结果渲染，不含业务逻辑；后端负责全部处理逻辑。
- 后端三层：总处理层（调度模块、组装结果）、基础支撑层（算法/存储/缓存，存储只定义接口）、可插拔功能模块层。
- 可插拔功能模块：网络热点追踪模块、通用知识模块（大模型，可切换适配器）、知乎专有模块（站内讨论）、语音模块（预留）。
- 模块接口：name / canHandle(请求类型) / execute(输入)，总处理层只依赖接口，新增模块实现接口并注册即可。
- 配置驱动：配置文件控制模块启停与模型选择，切换只改配置不改代码。
```

## 二、四个方向的本质（最重要的认知，防跑偏核心）

**四个方向不是「答案的四个角度」，而是「去找参考资料的四个渠道」。**

| 方向 | 原话 | 它负责去找什么资料 | 默认资料源链（主 → 兜底） |
|---|---|---|---|
| `term` 术语解释 | 解释专业名词/黑话 | 词义/黑话释义 | LLM |
| `hotspot` 热点关联 | 说明热点事件/历史背景 | 事件背景、时间线 | 热榜 → 全网搜索 → LLM |
| `subtext` 潜台词解读 | 隐含意思、梗、阴阳怪气 | 梗的由来、言外之意 | LLM → 知乎搜索 |
| `community` 社区理解 | **AI 信息不足时**结合用户讨论 | 知乎站内其他人怎么讨论 | 知乎搜索 → 知乎评论 → LLM |

三条由此推出的铁律：

1. **四个方向可并行、可叠加，不是互斥单选。** 一段话可能同时需要「这是什么事」（热点）+「大家怎么看」（社区），两个渠道都该跑，不该二选一。
2. **「社区理解」是兜底渠道，不是并列输出角度。** 它要解决的是「AI 自己对这事拿不准/答不深」——去知乎站内补真实用户视角，而不是「判断文本属不属于社区共识类」。
3. **四个方向只是初始想法，随时可微调、增减。** 方向必须可插拔（配置驱动），换场景就换清单（脱离知乎 → 去掉 community）。

## 三、看文本的三层（输出组织框架）

> 「看一段文本」= 三层，是**通用的输出组织框架**，不限于知乎：

| 层 | 含义 | 知乎里的实例 |
|---|---|---|
| **a 本意** | 字面在说什么 | 一句话人话（`lead`） |
| **b 引申** | 多方向的言外之意 | 术语 / 热点 / 潜台词 / 社区（四方向的检索结果） |
| **c 位置·时间·评论** | 在什么语境里说的 | 位置 = 所在回答/问题；时间 = 写作时间；评论 = 读者怎么反应 |

**c 是通用标准，知乎只是它的一种实例**：换到新闻上，c 就变成「哪个媒体、哪天发的、评论怎么说的」。

**与四方向的关系**：四方向（term/hotspot/subtext/community）= **检索渠道**，服务于 **b「引申」** 这一层；三层 = 更高的**输出组织框架**。

**综合器的职责**：拿到所有方向的信息点后，先统一判断「哪些和选中文本相关」，只组织相关的；再按 **本意 → 引申 → 语境** 三层组织输出。无料方向不引申，自然回到本意收尾（字面直白就一句本意，不灌长文）。

## 四、核心架构转变（推翻旧认知的地方）

| | 旧认知（已作废） | 新认知（现行） |
|---|---|---|
| 定位 | 划词 → **路由判断属于哪一类** → 走那条路生成答案 | 划词 → **并行让所有方向检索** → 综合器组织 |
| 四个方向 | 融合正文里的「检查清单」 | 可插拔的「检索模块」 |
| 路由模块 | 单选分类器（`router.ts`） | **整个删除** |
| 输出 | 固定「一句话 + 融合正文」两段 | 综合器自由组织（markdown，形式多变） |
| 证据 | 按 route 判断调哪些 provider | 每个方向挂一条资料源链，自己降级 |

**为什么路由必须删**：单选路由假设一段话只属于一个方向。典型反例「俄罗斯给印度公民免签」——它是「一件已发生的事」（热点关联该上），也可能让人想问「大家怎么看」（社区该补），单选路由逼它二选一，判成 community 后热点那条渠道就被掐掉了。根因是架构错，不是判得准不准。

**方案施工图**：[10-方向重构方案.md](./10-方向重构方案.md)（三层架构、类型定义、任务 D1–D9）。

## 五、不可动摇的产品原则

1. **核心能力不依赖知乎接口**：任何方向都挂 LLM 兜底，接口断了自动降级，产品仍能运行。
2. **方向只找料，综合器才说话**：方向零耦合，只返回结构化信息点；唯一产出答案的地方是综合器。
3. **不编造**：证据有出处（`[ref:N]`），没料就说「站内讨论不多」，绝不写「知乎用户普遍认为」。
4. **划词即解析，不用会问**：一句话价值主张是「别人做问 AI，言外做不用会问」。
